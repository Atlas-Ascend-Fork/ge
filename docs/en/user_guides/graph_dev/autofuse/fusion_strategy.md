## Overview

The fusion strategy needs to comprehensively consider backend capabilities, performance gains, and memory peak impact to make decisions on fusion behavior and perform fusion processing, thereby obtaining a relatively optimal fusion result. The functions currently implemented by the fusion strategy are as follows:

- Supports unified fusion rule determination.
- Supports dynamic and static shapes (depending on [symbolization](symbolization.md)).
- Supports fusion scale control.
- Supports fusion priority processing.

The fusion strategy module consists of two parts: the CanFuse framework and the Backend:

- **CanFuse framework**: supports fusion determination (cycle detection, memory peak, etc.) and fusion strategy solving.
- **Backend**: supports fusion rules and fusion processing (loop fusion, AscGraph fusion, and AscBackend fusion).

The main interaction process between the two parts is as follows:

**Figure 1** CanFuse and Backend interaction process
![Figure 1](../figures/canfuse_backend_interaction_flow.png "CanFuse and Backend interaction process")

The fusion performed by the [Lowering](lowering.md) module is the first-stage fusion, and the fusion performed by the CanFuse framework is the second-stage fusion. The brief process of the second-stage fusion is as follows:

1. Perform a round of fusion first, with 10 rounds by default.
2. Obtain all node pairs that may be fused.
3. Obtain the fusion priority from the fusable node pairs obtained in the previous step.
4. Sort the node pairs based on the priority and the fusion strategy score.
5. Call the CanFuse framework to determine the fusion rules:
    1. Determine whether vertical fusion can be performed.

        Vertical fusion: There is an input-output relationship between two fusion nodes, where the output of one node serves as the input of the other.

    2. Analyze the impact on the memory peak.
    3. Determine whether horizontal fusion can be performed.

        Horizontal fusion: The two nodes have no input/output relationship, but both receive inputs from the same root node.

6. Fuse the two nodes.

## Fusion Condition Determination

To determine whether two nodes can be fused, the determination results of both the CanFuse framework and the Backend must be considered. Fusion is allowed only when both results indicate fusion support. This section describes the determination conditions of each.

### Fusion Condition Determination Using the CanFuse Framework

- Reduces memory reads and writes

    Nodes that can be fused must share memory. For example, as shown in the following figure, output 1 of Node1 is the input of Node3, so they can be fused; the inputs of Node3 and Node4 both come from output 1 of Node1, so they can be fused. After fusion, memory movement can be saved in both cases. Although the inputs of Node2 and Node3 both come from Node1, they do not come from the same output of Node1. After fusion, the data still needs to be moved in twice, which does not reduce memory movement. Therefore, they cannot be fused.

    **Figure 1**  Determination of fusion condition 1 using CanFuse
    ![Figure 1](../figures/canfuse_fusion_condition_1.png "Determination of fusion condition 1 using CanFuse")

- Does not cause a cycle

    As shown in the following figure, fusing Node1 and Node3 would cause a cycle, so they cannot be fused.

    **Figure 2**  Determination of fusion condition 2 using CanFuse
    ![Figure 2](../figures/canfuse_fusion_condition_2.png "Determination of fusion condition 2 using CanFuse")

- Does not exceed the maximum fusion count limit (the default maximum fusion count is 64)

    Fusion scale control is mainly intended to prevent backend resources from being exceeded. The node count is controlled based on the number of nodes in the AscGraph generated by Lowering. For example, in the following figure, after Node1 and Node2 are fused, the total number of nodes is considered to be 9, so they can be fused. If the total number of nodes after fusing two nodes exceeds the threshold, they cannot be fused.

    **Figure 3**  Determination of fusion condition 3 using CanFuse
    ![Figure 3](../figures/canfuse_fusion_condition_3.png "Determination of fusion condition 3 using CanFuse")

- Does not increase the memory peak

    Excessive fusion may increase the memory peak, so a balance must be struck between execution performance and memory usage. A complete memory peak evaluation is a relatively complex process. For now, a simple strategy is used for evaluation: nodes whose span (the difference in topological sorting IDs) exceeds the configured threshold are no longer fused. When nodes can be fused horizontally, the output memory of the fused node is first calculated to check whether it exceeds 13 GB. If it exceeds 13 GB, the nodes are not fused.

    For example, as shown in the following figure, memory reuse is possible between Node2 and NodeN before fusion, but after fusion the memory peak increases. Therefore, these nodes cannot be fused.

    **Figure 4**  Determination of fusion condition 4 using CanFuse
    ![Figure 4](../figures/canfuse_fusion_condition_4.png "Determination of fusion condition 4 using CanFuse")

### Backend Fusion Condition Determination

- The loop axes of the two AscGraphs must be mappable.

    The first condition for fusion is whether the loop axes of the two AscBackends can be mapped. If they do not belong to the same set of loop axes, fusion determination is meaningless. Because each AscBackend is lowered independently, its loop axis IDs are also numbered independently, which may lead to inconsistent axis IDs. A typical scenario is shown in the following figure: after AscBackend1 performs a reduce operation, it has one fewer loop axis. In AscBackend2, z1 corresponds to z2 in AscBackend1, and z2 corresponds to z3 in AscBackend1. To fuse them, the loop axes in AscBackend2 must be adjusted to match those in AscBackend1.

    **Figure 5**  Determination of the fusion condition using Backend
    ![Figure 5](../figures/backend_fusion_condition.png "Determination of the fusion condition using Backend")

- The two AscGraphs must satisfy the Schedule group merge rules.

    Assume that the axes are abstracted into three groups: xgroup, ygroup, and rgroup, where:

  - **xgroup:** A separate group introduced for Concat-type operators. The axes before the Concat axis belong to xgroup, and those after it belong to ygroup.
  - **ygroup:** The loop axes of Elementwise and Broadcast type operators.
  - **rgroup:** The set of Reduce axes.

    Each AscGraph has an \(xgroup, ygroup, rgroup\) based on its loop axes. According to the operator fusion rule derivation, it can be determined whether two AscGraphs can be fused into a new group. CanFuse then uses this rule to determine whether the backend Schedule supports the fusion. For details about the group merge rules, see [Generating TilingCase](schedule.md#generating-tilingcase).

## Fusion Strategy Solving

After [fusion condition determination](#fusion-condition-determination), if two nodes are found to be fusible, multiple combinations of fusion results may be produced, such as fusion strategy 1 and fusion strategy 2 in the following figure. When multiple fusion strategies exist, it is necessary to determine which strategy is optimal.

**Figure 1**  Multiple fusion strategies
![Figure 1](../figures/multi_fusion_strategy_scenario.png "Multiple fusion strategies")

Computing the optimal solution of the fusion strategy for the entire graph is rather difficult, mainly for the following two reasons:

1. The algorithm complexity may be high. One feasible approach is to solve it using dynamic programming, which is difficult to guarantee in nlog\(n\).
2. The performance estimation model is inaccurate. Without actual on-board testing, it is difficult to accurately determine the real performance after fusion.

For the above reasons, pursuing a strict global optimal solution inevitably involves a large number of whole-graph fusion attempts and on-board measurements, which significantly increases the time complexity. Therefore, at the current stage, a **simple fusion strategy solving algorithm based on score + greedy** is adopted: pair the fusible nodes in the graph, perform CanFuse determination on each pair one by one, and when fusion is possible, sort them by score (to determine the order of fusion), and finally perform fusion processing in sequence. The nodes after the first round of fusion will repeat this processing again, attempting multiple rounds of fusion, with a maximum of 10 rounds. The fusion scoring rules are as follows:

1. Calculation of the saved memory size (using symbols to implement size comparison; the larger the value, the higher the priority).
2. Calculation of the proximity between nodes (using the difference of topo order IDs; the smaller the value, the higher the priority).

Sorting priority:

First compare the memory size; when the memory sizes are equal, compare the proximity; if the proximity is also equal, sort in ascending order by topo order and perform deduplication, finally obtaining the fusion-capable node pairs, which will be processed for fusion in this order subsequently.

Take [Figure 2](#fig1) and [Figure 3](#fig2) as examples to briefly illustrate the use of the greedy algorithm:

As shown in [Figure 2](#fig1), A, B, C, and D form the AB, BC, and CD fusion node pairs. After sorting, the fusion order is determined. Assuming the fusion order is CD first and AB second, after fusion they become CD and AB; when processing the BC fusion, B has already become AB and C has already become CD, finally resulting in the fusion processing of AB+CD.

**Figure 2**  Fusion example 1<a id="fig1"></a>
![Figure 2](../figures/fusion_example_1.png "Fusion example 1")

As shown in [Figure 3](#fig2), if the order is AB first and BC second, the fusion process changes. AB is fused first; when processing the BC fusion, since B has already become AB, the fusion of AB+C is performed, resulting in ABC. Similarly, the CD fusion performs the fusion of ABC+D.

**Figure 3**  Fusion example 2<a id="fig2"></a>
![Figure 2](../figures/fusion_example_2.png "Fusion example 2")

The final fusion results of the two scenarios are the same, both being ABCD. However, assuming that A and D cannot be fused, the actual results differ: the result of [Figure 2](#fig1) is AB and CD, while the result of [Figure 3](#fig2) is ABC and D. It can be seen that changes in the fusion order lead to differences in the fusion process and results. The current algorithm also has limitations: the current greedy algorithm considers only the local optimum, which may result in a non-optimal global solution. For example, when A and D cannot be fused, if CD is fused first, ABC may fail to fuse, which may not be the optimal strategy from a global perspective.

## Fusion Node Processing

Fusion can be performed only between AscBackend nodes. After fusion, if loop axis fusion is possible, the result is still of the AscBackend type; if loop axis fusion is not possible, a FusedAscBackend type is generated.

Node fusion requires fusing the AscBackend nodes in the original graph and, at the same time, performing subgraph fusion on the AscGraph under each AscBackend. During subgraph fusion, the load and store nodes on the AscGraph must be eliminated. The principles for processing fusion nodes are as follows, and the schematic diagram is shown in [Figure 1](#fig1).

- Determine whether two AscBackend nodes can undergo loop axis fusion based on whether their loop axes are the same. If loop axis fusion is possible, merge the two AscGraphs under the AscBackend nodes. (For the specific merge process, see [Figure 2](#fig2).)

- If loop axis fusion is not possible, place the AscBackend into the subgraph of a new FusedAscBackend, and let the backend decide whether to generate multiple kernels or a single kernel containing multiple loops.
- A FusedAscBackend that cannot undergo loop fusion is directly fused with an AscBackend in the original graph into a new FusedAscBackend.
- The subgraph of a FusedAscBackend may still contain AscBackend nodes that can undergo loop fusion. The framework should perform loop axis fusion as much as possible.
