## Introduction to Symbolization

### What Is Symbolization

Symbolization refers to expressing the shape of operators through symbols, and provides simplification, derivation, and Guard functions. Automatic fusion requires symbolization to be performed first. After symbolization, the semantics of some operators can be retained, providing key information for the subsequent loop axis merging and memory optimization phases.

### Basis of Symbolization

To support symbol expression computation and simplification, the current automatic fusion encapsulates the open-source C++ SymEngine library. The advantage of this encapsulation layer is that it maintains usage stability, avoids binding to open-source modules, and allows flexible replacement with other third-party libraries or self-developed libraries in the future.

### Symbolization Generation

At compile time, before entering automatic fusion, all inputs on the graph are first symbolized to generate symbols. After this phase, shape inputs such as Data and RefData on the graph carry generalized symbol shape inputs. The specific symbolization logic is as follows: if the value is greater than 0, it is symbolized as a **constant symbol**; -1 is symbolized as a **dynamic symbol**, with the first -1 symbolized as s0, the second -1 symbolized as s1, and so on in ascending order.

For example, [Figure 1](#fig1) has three inputs, whose shapes before and after symbolization are as follows:

- data0: \[3, -1\] -\> \[3, s0\];
- data1: \[-1, 5\] -\> \[s1, 5\];
- data2: \[-1, -1\] -\> \[s2, s3\].

### Symbol Propagation

Symbol propagation is symbol derivation. Each node derives the symbolization shape of its output based on the symbolization shape of its input. Symbols are generated by Data nodes and then propagated along the nodes in the graph to derive the symbolization output shape of each node step by step until the entire graph is traversed. Symbol propagation involves the following cases:

- InferSymbolShape derivation (class-1 operator processing): derives the symbolization shape of the output based on the input symbol shapes of the operator.

    For example, in the following figure, Concat has two inputs whose symbolization shapes are data0\[s0, s1\], data1\[s0, s2\], and concat\_dim is 1. Based on the function of the Concat operator, its output shape can be derived as \[s0, \(s1 + s2\)\].

    **Figure 2**  Class-1 operator processing
    ![Figure 2](../figures/type1_op_processing.png "Class-1 operator processing")

- InferValue derivation (class-2 operator processing): performs symbol folding on the graph.

    A class-2 operator is one whose output symbol can be derived at compile time, but the output derivation is value-dependent. The output symbol cannot be derived from the input shape symbols alone; in addition to the input symbols, the input values are also required to derive the output. For example, as shown in [Figure 3](#fig2), to derive the symbolization shape of the BroadcastTo operator, it is necessary to know not only the output shape of the Pack node but also its output value.

    **Figure 3**  Class-2 operator processing<a id="fig2"></a>
    ![Figure 3](../figures/type2_op_processing.png "Class-2 operator processing")

    Since symbols are generated during compilation, for class-2 operators (such as ReShape), constant folding can be extended by registering the corresponding symbol folding kernels to implement symbol-based folding operations at compile time, thereby completing symbol-based kernel computation and InferValue logic. The brief logic of constant folding is as follows:

    1. Register the kernel functions of operators that support symbol computation, such as Add, Sub, Mul, and Shape.
    2. Refer to constant folding processing to traverse the entire graph. If all input nodes of a node can obtain specific values, call the symbol kernel function corresponding to the current node\_type to perform a round of folding computation.
    3. After the current node is folded, set the symbol value to the peer output Tensor of the node. After symbol folding is complete, because these expressions are all Host-side computations on shape, these nodes can be optimized out during compilation, thereby reducing scheduling and dispatch during execution.
    4. Continue the folding computation.

- Processing of class-3 and class-4 operators:

    Class-3 and class-4 operators refer to those whose output symbols cannot be derived from the input shape or symbol value at compile time, and whose specific output shape can be determined only after actual execution. In the automatic fusion scenario, for class-3 and class-4 operators, you can enable graph-splitting compilation (refer to the **--experimental\_enable\_jit\_executor\_v2** control item in [Enabling AutoFuse](autofuse_enable.md)).

- Processing of custom operators:

    1. If the symbol derivation process of a custom operator is not supplemented, the operator is processed in the same way as the class-3 and class-4 operators described above.
    2. If the symbol derivation of a custom operator is supplemented, class-1 and class-2 operators are derived as normal class-1 and class-2 operators, and class-3 and class-4 operators are also processed by Fallback.

    After compilation, symbol expressions are generated. In the execution phase, GE needs to complete shape derivation and memory allocation based on the actual Dim values corresponding to the symbols. Therefore, how to perform actual shape computation based on symbols in the execution phase is a key point.

At the functional implementation level, symbolization is divided into symbol derivation and symbol computation. The priority is to perform symbol computation first, then symbol derivation. If neither exists, static derivation is performed. The order is as follows:

1. Symbol computation

    Refers to the ability to derive both the output shape and the output value of an operator. For example, for the Shape operator, when the shape of the input data is \[s0, 4\], its output shape is \[2\], and its output value is \{s0, 4\}.

2. Symbol derivation

    If the operator cannot derive its output value, it attempts to derive only the output shape.

3. Static derivation

    If none of the above methods can perform derivation, determine whether the output shape of the operator is static. If it is static, the static operator can be directly used as the result of its symbol derivation. If it is not static, the operator cannot be derived, and symbol derivation and symbol computation functions need to be added to the operator.

## Guard Mechanism and Principle

### Background

In the current framework, dynamic dimensions in operator input and output shapes are usually represented by -1, but this method can express only limited information. Therefore, symbols (such as s0 and s1) are used to represent unknown dimensions, and these symbols can express more information than -1. For example, as shown in the following figure, after the input shapes of Data0, Data1, and Data2 are symbolized, the output shape of Add can also be expressed by symbols, so that the output shape of its next node Mul can be computed. Compared with a shape of -1, the output shape of Mul can express more information in this case.

**Figure 1** Symbolization example
![Figure 1](../figures/symbolization_example.png "Symbolization example")

However, the current symbolization expression may have problems in the following two scenarios:

- **Scenario where Assert validation needs to be performed on symbol shapes**

    During symbol derivation, some operators require strong validation of certain dimensions. For example, for the Matmul operator in the following figure, the input symbol s1 must be equal to s2. Otherwise, undefined behavior (such as out-of-bounds access or errors) will occur when the Matmul operator is executed.

    **Figure 2** Symbolic shape to be verified by Assert
    ![Figure 2](../figures/symbolic_shape_assert_check_scenario.png "Symbolic shape to be verified by Assert")

- **Broadcast scenario**

    The computation of some operators requires broadcast (for example, Add and Mul). For example:

    **Figure 3** Broadcast
    ![Figure 3](../figures/broadcast_scenario.png "Broadcast")

    In this scenario, because both s1 and s3 are symbols, the magnitude relationship between s1 and s3 cannot be determined during symbol derivation, and only the following three cases satisfy Broadcast. In addition, during compilation, it is impossible to determine which branch should be executed. If the branch condition is not met at execution time, undefined behavior (such as out-of-bounds access or an error) may occur.

    $$
    \mathrm{output\_shape} =
    \begin{cases}
    [s0, s1] & s3 = 1 \\
    [s0, s1] & s1 = s3 \\
    [s0, s3] & s1 = 1
    \end{cases}
    $$

    To address the two problems above, the concept of "**Guard**" is introduced. With Guard, we can explicitly express the direct relationship between symbols. For example, in the Broadcast scenario above, the symbol relationship expression s1 == s3 can be used to indicate that the current Broadcast path is s1 == s3, and all subsequent symbol derivation is performed based on this path. During execution, if the values substituted into the symbols do not satisfy s1 == s3, the current model compilation result cannot be used directly and the model must be recompiled. This is one of the usage scenarios of Guard.

### Hint Value

Before understanding the Guard principle, let us first understand what a hint value is: a hint value is a hint value passed in by the user during online execution, usually the input shape passed in by the user during the current iterative execution (this shape is definitely known), for example, the following model:

**Figure 4** Hint value diagram
![Figure 4](../figures/hint_value_diagram.png "Hint value diagram")

In the model, some dimensions of Data0, Data1, and Data2 are unknown, but during iterative execution, the user passes in input tensors with static shapes, and these shapes can serve as references for symbol Guards at compile time. For example, when compiling the above figure, the shape of Data0 is \[2, 3, 4, 2\], the shape of Data1 is \[2, 3, 1, 2\], and the shape of Data2 is \[2, 3, 1, 2\]. Therefore, when compiling the model, the hint value of s0 is 2, the hint value of s1 is 3, the hint value of s2 is 4, the hint value of s3 is 2, and the hint value of s4 is 1. Usually, each symbol has a hint value, and the Guard mechanism is implemented based on these hint values. According to different functions, Guards are mainly divided into expect\_guard and assert\_guard:

- expect\_guard: mainly expresses what relationship the symbols need to satisfy for the current model to be executable, and is mainly used for branch validation. When this Guard condition is not satisfied, the model triggers recompilation.
- assert\_guard: mainly used for strong symbol validation. If a symbol does not satisfy this Guard, the model cannot be executed at all even if it is recompiled, and the process is interrupted with an error.

### Guard Fundamentals

The Guard mechanism is implemented based on symbol relation expressions (for example, s0 == s1), and is mainly used to express the magnitude relationship between two symbol computation expressions. A Guard is graph-level. Once such a Guard is generated during graph compilation, the symbol values passed in when executing the graph compilation result must satisfy the expression; otherwise, execution will fail.

1. **How is a Guard generated?**

    This is where the hint value mentioned earlier comes into play. Because the value of a symbol itself is unknown, it cannot be directly compared in magnitude, but each symbol has a hint value. At compile time, when it is necessary to determine whether a symbol relation expression holds, we can perform the computation using the hint values. For example:

    It is necessary to verify whether s0 + s1 equals s2. Direct comparison cannot determine whether s0 + s1 equals s2, but if the hint values are substituted into the expression, the computation can be performed. For example, if the hint value of s0 is 2, the hint value of s1 is 3, and the hint value of s2 is 5, then s0 + s1 equals s2, and a Guard of s0 + s1 == s2 can be generated. Conversely, if the hint value of s0 becomes 3, then s0 + s1 does not equal s2, and a Guard of s0 + s1 != s2 needs to be generated. These Guards are stored in the graph compilation result, and their lifecycle is consistent with that of the graph.

2. **After a Guard is generated, how is it used in the execution phase?**

    Suppose a Guard of s0 + s1 == s2 is generated during the compilation phase. Note that this Guard is generated based on the iterative input values at compile time. That is, when the model has a dynamic shape, the symbol values of subsequent iterations will change. For example, when executing a model whose inputs are Data0:-1,-1; Data1:-1,-1, after the input shapes of this model are symbolized, they become Data0:s0,s1; Data1:s2,s3. When this model is executed online:

    1. step0: Graph compilation needs to be performed. At this time, the execution input shapes are Data0:2,3; Data1:5,2. Therefore, during graph compilation, the hint value of s0 is 2, the hint value of s1 is 3, the hint value of s2 is 5, and the hint value of s3 is 2. At this point, in the compilation state, a Guard of s0+s1 == s2 is generated based on the symbol hint values of the current step and saved in the graph compilation result.
    2. step1: If the execution input shapes remain unchanged, the Guard generated in step0 will definitely pass validation, and the graph compilation result of step0 can be executed directly.
    3. step2: Suppose the input shapes become Data0:3,4; Data1:7,2. At this time, the value of symbol s0 becomes 3, s1 becomes 4, and s2 becomes 7. Although the symbol values have changed, the Guard of s0+s1 == s2 still holds. Therefore, the graph compilation result of step0 can still be executed directly.
    4. step3: If the input shape changes to Data0:5,4; Data1:7,2, the value of symbol s0 becomes 5, and the Guard s0+s1 == s2 is false, so this Guard is not satisfied. Therefore, the graph compilation result of step0 can no longer be used, and the model needs to be recompiled based on the input values of the current step.

### Guard Usage Scenarios

Now that you understand what Guard is, in which cases do you need to use Guard? Currently, Guard is mainly used in the following scenarios:

- **Broadcast scenario**

    The most common usage scenario of Guard is the Broadcast scenario. When performing Broadcast, the symbol alone cannot determine whether Broadcast needs to be executed. Therefore, the Guard function is needed to make the judgment. For example, in the following Add operator computation scenario:

    **Figure 5** Guard usage scenario 1
    ![Figure 5](../figures/guard_usage_scenario_1.png "Guard usage scenario 1")

    The output of the current Add may have three possible cases:

  - When s0==s1, the output shape of the Add operator is \[s0, 2\].
  - When s0==1, the output shape of the Add operator is \[s1, 2\] (the dimension of 1 needs to be broadcasted).
  - When s1==1, the output shape of the Add operator is \[s0, 2\].

    Therefore, a Guard can be generated based on the hint values of s0 and s1, and the generated Guard is used to determine the output shape of the Add operator. For example:

  - When the hint value of s0 is 2 and the hint value of s1 is also 2 (that is, the hint value of s0 equals the hint value of s1), the symbol derivation function of Add needs to generate an expect\_guard of s0==s1, and the output shape of Add is \[s0, 2\].
  - When the hint value of s0 is 1 and the hint value of s1 is 2, the symbol derivation function of Add needs to generate an expect\_guard of s0==1, and the output shape of Add is \[s1, 2\].
  - When the hint value of s0 is 2 and the hint value of s1 is 1, the symbol derivation function of Add needs to generate an expect\_guard of s1==1, and the output shape of Add is \[s0, 2\].

    In addition, during subsequent iterative execution, if the input shape changes and the current Guard is no longer satisfied, the model needs to be recompiled.

- **Strict shape verification**

    Some operators impose certain constraints on the input shape, in which case an assert\_guard is required. For example, consider the Matmul operator shown in the following figure: during its computation, the first dimension of the 0th input must equal the 0th dimension of the 1st input; otherwise, the operator cannot perform the computation. Therefore, the input symbol s1 must equal s2. During the compilation phase, an assert\_guard of s1==s2 is generated based on the hint values of s1 and s2. If the hint values of s1 and s2 do not satisfy this Guard condition, the program reports an error and aborts.

    **Figure 6**  Guard usage scenario 2
    ![Figure 6](../figures/guard_usage_scenario_2.png "Guard usage scenario 2")

- **Divisibility check**

    In addition to the two usage scenarios described above, some operators, such as the Reshape operator, also need to verify whether the shape supports divisibility. For example, in the scenario shown in the following figure: one input shape of Reshape is \[s0, s1\], and the other input is a Const whose shape is \[2\] and whose value is \[2, -1\]. In this case, for Reshape to be computable, an assert\_guard of Mod\(s0\*s1,2\) == 0 must be satisfied; otherwise, this Reshape cannot be computed.

    **Figure 7**  Guard usage scenario 3
    ![Figure 7](../figures/guard_usage_scenario_3.png "Guard usage scenario 3")

- **Boundary check**

    When some operators require a symbol value to fall within a certain range, Guard can also be used for control. For example, consider the Slice operator in the following figure: the shape of the input x of this Slice operator is \[s0, s1\], the value of offset is \[2\], and the value of size is 2. Since the value of offset must fall within the interval \[0, s0\], an assert\_guard of 2<= s0 needs to be generated.

    **Figure 8**  Guard usage scenario 4
    ![Figure 8](../figures/guard_usage_scenario_4.png "Guard usage scenario 4")

### Guard Derived Capabilities

After Guards are generated through symbol derivation, some additional functions can be provided based on Guards:

- **Symbol Simplification**

    With the Guard capabilities described above, symbols can be simplified based on Guards. For example, when a Guard s2==s0+s1 exists, s0+s1 can be used to replace s2. In addition, the symbol equivalence union-find function is supported. For example, given two Guards s2==s0+s1 and s0==2, s2 can be simplified to 2 + s1.

- **StaticCheck Function**

    During the compilation phase, some static comparisons of symbols need to be performed based on the existing symbol Guard relationships. Therefore, symbolization provides the StaticCheck function. When the static\_check API is called, the following two steps are performed:

    1. First, determine whether the relational expression is a constant expression. If it is, directly return the determination result.
    2. Second, if the expression is not a constant expression, check whether the Guard currently exists. If it exists, return the Guard result; otherwise, return false.
