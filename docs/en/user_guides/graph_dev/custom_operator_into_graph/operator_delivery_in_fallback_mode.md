# Operator Delivery in Fallback Mode

## Overview

The Atlas 200I/500 A2 inference product **does not support this feature**.

GE provides two conventional model scheduling modes (sinking scheduling and Host scheduling) to implement efficient collaboration between the Host and the Device.

The sinking scheduling mode is generally applicable to static-shape models. Because the input tensor shapes are fixed, memory orchestration and Tiling computation can be completed at the compilation stage. Therefore, the operators in the model can be delivered to the Device as a whole graph. During execution, only one Task for model execution needs to be delivered on the Host side to trigger the model to be scheduled and executed on the Device, thereby improving model scheduling performance.

The Host scheduling mode is generally applicable to dynamic-shape models. Because the shapes of the input tensors are uncertain, the input shape and other information of the next operator can be determined only after the shape derivation of the previous operator is completed. Therefore, the entire model cannot be executed in a sinking manner, and each operator Kernel usually needs to be delivered to the Device one by one for execution.

Delivering operators based on fallback is a type of Host scheduling mode. Users can execute operators on the Host side through fallback functions, for example, by directly calling the aclnnXX single-operator API to execute operators. Users only need to call the Ascend C [EnableFallBack](https://gitcode.com/cann/asc-devkit/blob/9.2.0/docs/zh/api/README.md) API during operator development to automatically generate a fallback function for GE to call back. The main task of the fallback function is to convert the inputs, outputs, and attributes of GE into the parameter format required by the aclnnXX single-operator API, and then call the aclnnXX API to execute the operator.

## Applicable Scenarios

- Offline inference scenarios are not supported. This feature applies only to training or online inference scenarios.
- It is generally recommended to enable fallback delivery for multi-kernel operators in dynamic-shape models. The main reasons are as follows:
  - In static-shape scenarios, the aclnnXX API includes Host operations and cannot be delivered as a whole graph. It needs to be delivered as a subgraph after graph splitting, which may have a significant impact on performance.
  - In rare cases, to achieve ultimate performance optimization of an operator, operator developers develop multi-kernel operators (such as the built-in Matmul and MC² operators of Ascend). Such an operator corresponds to multiple kernel implementations and needs to launch multiple kernels during execution. Because the number of kernels is uncertain, GE cannot process them uniformly in the conventional manner described above. Therefore, the operator must be delivered in fallback mode.
  - For single-kernel operators, enabling the fallback delivery mode may degrade performance. Currently, the aclnnXX APIs automatically generated by the Ascend C custom operator project are all single-kernel operator APIs. Therefore, it is not recommended that users enable fallback delivery for these operators.

The main task of the fallback function is to convert the inputs, outputs, and attributes of GE into the parameter format required by the aclnn single-operator API, and then execute the operator by calling the aclnnXX API. Taking the concat operator as an example, the format of the fallback function is as follows:

```c++
static graphStatus ConcatExecuteFunc(OpExecuteContext* host_api_ctx)
```

The OpExecuteContext pointer input parameter mainly contains the information required for computing the fallback, such as the shape and datatype of the inputs and outputs. For details, see [Basic Data Structures and APIs](https://gitcode.com/cann/metadef/blob/9.2.0/docs/en/api/README.md)\>"gert namespace \>OpImplSpaceRegistryV2 class".

Users do not need to manually implement the fallback function. During operator prototype registration, they only need to call the EnableFallBack API, and the system automatically generates the fallback function and registers it with GE.

## Usage Guide

1. During operator development, call the Ascend C `EnableFallBack` API in the operator prototype registration process to automatically generate the fallback function:

    ```c++
    class CustomOp : public OpDef {
    public:
        CustomOp(const char* name) : OpDef(name)
        {
            // Define the input/output information of the operator, including whether it is mandatory and the DataType and Format supported by the input/output.
            this->Input("x").ParamType(REQUIRED).DataType({ge::DT_FLOAT}).Format({ge::FORMAT_ND});
            this->Input("y").ParamType(REQUIRED).DataType({ge::DT_FLOAT}).Format({ge::FORMAT_ND});
            this->Output("z").ParamType(REQUIRED).DataType({ge::DT_FLOAT}).Format({ge::FORMAT_ND});
            // Register the shape inference function.
            this->SetInferShape(ge::InferShapeFunc);
            this->SetInferDataType(ge::InferDataTypeFunc);
            // Register the AI processor models supported by the operator through AddConfig.
            this->AICore().AddConfig("ascendxxx");
            this->EnableFallBack();
        }
    };
    OP_ADD(CustomOp);
    ```

    The current fallback function supports two call modes: support\_aclnn and aclnn\_only. They can be configured through the `aclnnSupport.value` parameter of the `ExtendCfgInfo` API. For details, see [Ascend C API](https://gitcode.com/cann/asc-devkit/blob/9.2.0/docs/zh/api/README.md).

    - support\_aclnn: In this mode, the operator is executed through model sinking in static shape scenarios, while in dynamic shape scenarios the fallback function is called on the Host side to deliver the operator. This mode is used by default if `EnableFallBack` is called.
    - aclnn\_only: In this mode, the operator is delivered in fallback mode in both static and dynamic shape scenarios. This mode is not recommended and will be deprecated in later versions.

2. During training or online inference based on the GE graph mode, the fallback function is automatically called back to execute the relevant operators.

## Function Debugging

The key logs in support\_aclnn mode and aclnn\_only mode are as follows:

```text
xxx, setting fallback attribute
```
