# OM2 Header Reference

This document covers `om2_model_api.h`, `gert_model_data.h`, and `om2_package_contants.h`. Part I describes the runtime C API of the model SO; Part II describes model data structures and package path constants.

## Part I: OM2 Model SO C API (om2_model_api.h)

### 1. Scope

This document describes all cross-boundary data structures and exported functions defined in `inc/framework/om2/model_api/om2_model_api.h`. This header is the **runtime C ABI contract between an OM2 model SO and the Executor**: the model SO implements and exports the declared C APIs, and the Executor binds and calls them by symbol name through `dlopen + dlsym`.

In this document, pbody refers to the model shared library generated by the code generator inside an OM2 package, that is, the model SO.

- **Compatibility rules**: Structure layout and symbol freezing rules are specified in Sections 1–8 of [OM2 Compatibility Rules](../../../../inc/framework/om2/README_en.md). This document references those rules where needed rather than repeating them.
- **Structure size**: `struct_size` denotes the byte range of the structure provided for this call, usually initialized to `sizeof(the actual structure type provided)`; it is not an independent version number.
- **Layout padding**: `abi_pad_N` is fixed layout padding, carries no business data, and must not be used to pass configuration.

### 2. pbody Interfaces (Exported by the Model SO, Called by the Executor)

pbody interfaces are C functions implemented and exported by the model SO. After `dlopen`, the Executor binds and calls them by symbol name through `dlsym`.

#### 2.1 GertModelHandle — Opaque Model Instance Handle

```c
typedef void *GertModelHandle;
```

- **Description**: Opaque handle to a model instance, returned through the `model_handle` argument of `GertModelLoad` (the Executor provides storage and pbody writes the value). Valid until `GertModelUnload` returns.
- The Executor must not dereference the handle or assume its internal layout; pbody is solely responsible for creating and destroying the handle.

#### 2.2 GertModelLoad

- **Description**: Creates a model instance, initializes resources, and sinks tasks to the device. pbody reads operator binaries, constant/variable addresses, and external resources from `config`, registers binaries, and allocates device memory. On success, it writes the instance handle to `*model_handle`. During initialization, pbody may invoke Executor callbacks through `config->callbacks`.
- **Prototype**:

```c
int32_t GertModelLoad(const GertModelLoadConfig *config, GertModelHandle *model_handle, GertModelLoadOutput *output);
```

- **Parameters**:

| Parameter | Type | Input/Output | Description |
|------|------|----------|------|
| config | const GertModelLoadConfig * | Input | Load parameters; must not be null. Fields are listed below |
| model_handle | GertModelHandle * | Output | Must not be null; initialize `*model_handle` to `nullptr` before calling. pbody writes the instance handle, which is used for execution after successful loading and becomes invalid after unloading |
| output | GertModelLoadOutput * | Reserved | Currently must be `nullptr`; pbody validates and rejects non-null values |

- **Return value**: `int32_t`; `0` indicates success, and nonzero values are failure codes. Do not execute the model after failure. The current implementation may write the instance handle before task sinking fails; call `GertModelUnload` to clean up a non-null handle in this case.

- **Parameter structure GertModelLoadConfig**:

| Field | Type | Description |
|------|------|------|
| struct_size | uint64_t | Byte range of the structure provided for this call; initialize to `sizeof(GertModelLoadConfig)` before calling |
| bin_files | const char ** | Array of operator binary file paths (UTF-8 strings) |
| bin_data | const void ** | Array of operator binary memory addresses (provided when loading binaries from memory) |
| bin_size | uint64_t * | Size of each binary in bytes |
| bin_num | uint64_t | Binary count, that is, the length of the bin_files/bin_data/bin_size arrays |
| constants | void ** | Array of device addresses for constants (weights), with a count matching the model's constants; may be null if there are no constants |
| var_addrs | void ** | Array of variable device addresses; may be null if there are no variables |
| work_ptr | void * | Workspace address (allocated and passed by the Executor for user-managed memory); may be null when unused |
| session_id | uint64_t * | Session ID pointer |
| model_id | uint64_t | Model ID, used only for logging and DFX |
| instance_handle | void * | Executor instance handle, passed back unchanged as the first argument when pbody invokes callbacks |
| callbacks | const GertModelLoadCallbacks * | Load-time callback collection; must not be null. Callbacks used by the binary cache path must be supplied; see Section 3 for individual nullability requirements |
| priority | int64_t | Model priority |
| reuse_zero_copy | uint64_t | Whether to reuse zero-copy resources; `0` means no, nonzero means yes |
| external_rt_model | aclmdlRI | External runtime model handle, provided for external resource management |
| external_streams | aclrtStream * | External stream array of length external_stream_num |
| external_stream_num | uint64_t | External stream count |
| external_events | aclrtEvent * | External event array of length external_event_num |
| external_event_num | uint64_t | External event count |
| external_labels | aclrtLabel * | External label array of length external_label_num |
| external_label_num | uint64_t | External label count |
| external_notifies | aclrtNotify * | External notify array of length external_notify_num |
| external_notify_num | uint64_t | External notify count |

- **Parameter structure GertModelLoadCallbacks**:

| Field | Type | Description |
|------|------|------|
| struct_size | uint64_t | Byte range of the structure provided for this call; initialize to `sizeof(GertModelLoadCallbacks)` before calling |
| report_model_base_info | ReportModelBaseInfoFunc | Reports the runtime model handle; see 3.1 |
| launch_func | GertModelLaunchFunc | Launches an individual task; see 3.2 |
| lock_bin_handle_store | LockBinHandleStoreFunc | Locks the binary handle cache; see 3.3 |
| unlock_bin_handle_store | UnlockBinHandleStoreFunc | Unlocks the binary handle cache; see 3.3 |
| query_bin_handle_from_store | QueryBinHandleFromStoreFunc | Queries a cached handle by bin_id; see 3.4 |
| save_bin_handle_to_store | SaveBinHandleToStoreFunc | Saves a handle to the cache; see 3.5 |
| release_bin_handle_from_store | ReleaseBinHandleFromStoreFunc | Releases a cached handle; see 3.6 |
| hccl_load_task | HcclLoadTaskFunc | Launches an HCCL communication task (HCOM/HVD); see 3.8 |

- **Parameter structure GertModelLoadOutput**:

| Field | Type | Description |
|------|------|------|
| struct_size | uint64_t | Structure size in bytes; currently has no other fields. This structure is reserved, and the Load output argument must be `nullptr` |

#### 2.3 GertModelRun

- **Description**: Synchronously executes a loaded model. After updating input/output-related addresses and the argument table, it executes the constructed model through `aclmdlRIExecute`. The current thread blocks until execution completes; the timeout is controlled by `config->stream_sync_timeout_ms`. Individual tasks are launched during loading, not repeatedly for each execution.
- **Prototype**:

```c
int32_t GertModelRun(GertModelHandle model_handle, const GertModelRunConfig *config, GertModelRunOutput *output);
```

- **Parameters**:

| Parameter | Type | Input/Output | Description |
|------|------|----------|------|
| model_handle | GertModelHandle | Input | Valid handle returned by `GertModelLoad` |
| config | const GertModelRunConfig * | Input | Execution parameters; must not be null. Fields are listed below |
| output | GertModelRunOutput * | Reserved | The current implementation neither reads nor populates this argument; may be `nullptr`. The Executor currently passes an initialized reserved output structure |

- **Return value**: `int32_t`; `0` indicates success, and nonzero values are failure codes.

- **Parameter structure GertModelRunConfig**:

| Field | Type | Description |
|------|------|------|
| struct_size | uint64_t | Byte range of the structure provided for this call; initialize to `sizeof(GertModelRunConfig)` before calling |
| input_count | uint64_t | Model input count |
| input_data | gert::Tensor ** | Array of model input Tensor pointers, of length input_count |
| output_count | uint64_t | Model output count |
| output_data | gert::Tensor ** | Array of model output Tensor pointers (output addresses filled in by the Executor), of length output_count |
| stream_sync_timeout_ms | uint64_t | Stream synchronization timeout for synchronous execution, in milliseconds |
| run_callbacks | const GertModelRunCallbacks * | Execution-time DFX callback collection; see below. Callback semantics are described in 3.7 |

- **Parameter structure GertModelRunCallbacks**:

| Field | Type | Description |
|------|------|------|
| struct_size | uint64_t | Byte range of the structure provided for this call; initialize to `sizeof(GertModelRunCallbacks)` before calling |
| report_run_info_preprocess | ReportModelRunFunc | DFX callback before model execution; see 3.7 |
| report_run_info_postprocess | ReportModelRunFunc | DFX callback after model execution; see 3.7 |

- **Parameter structure GertModelRunOutput**:

| Field | Type | Description |
|------|------|------|
| struct_size | uint64_t | Structure size in bytes; initialize to `sizeof(GertModelRunOutput)` when passing the reserved output object. No results are currently written back |

#### 2.4 GertModelRunAsync

- **Description**: Asynchronously executes a loaded model. After updating input/output-related addresses and the argument table, it submits model execution to the stream specified by `stream` through `aclmdlRIExecuteAsync`, without waiting for device execution to finish.
- **Prototype**:

```c
int32_t GertModelRunAsync(GertModelHandle model_handle, aclrtStream stream, const GertModelRunConfig *config,
                          GertModelRunOutput *output);
```

- **Parameters**:

| Parameter | Type | Input/Output | Description |
|------|------|----------|------|
| model_handle | GertModelHandle | Input | Valid handle returned by `GertModelLoad` |
| stream | aclrtStream | Input | Stream used for asynchronous execution |
| config | const GertModelRunConfig * | Input | Execution parameters; uses the same GertModelRunConfig structure as 2.3 |
| output | GertModelRunOutput * | Reserved | The current implementation neither reads nor populates this argument; may be `nullptr`. The Executor currently passes an initialized reserved output structure |

- **Return value**: `int32_t`; `0` indicates success (submission completed only), and nonzero values are failure codes.

#### 2.5 GertModelUnload

- **Description**: Destroys the model instance and releases its managed resources (device memory, operator binary references, streams, and so on). After successful unloading, `model_handle` is invalid. The Executor must complete Unload before calling dlclose on the model SO.
- **Prototype**:

```c
int32_t GertModelUnload(GertModelHandle model_handle, const GertModelUnloadConfig *config,
                        GertModelUnloadOutput *output);
```

- **Parameters**:

| Parameter | Type | Input/Output | Description |
|------|------|----------|------|
| model_handle | GertModelHandle | Input | Model instance handle to clean up; invalid after successful unloading. Passing it by value does not automatically clear the caller's stored handle |
| config | const GertModelUnloadConfig * | Reserved | Currently must be `nullptr`; a non-null value causes failure without destroying the instance |
| output | GertModelUnloadOutput * | Reserved | Currently must be `nullptr` |

- **Return value**: `int32_t`; `0` indicates success, and nonzero values are failure codes.

- **Parameter structures GertModelUnloadConfig / GertModelUnloadOutput**:

| Field | Type | Description |
|------|------|------|
| struct_size | uint64_t | Structure size in bytes; currently has no other fields. Both Unload config and output arguments must be `nullptr` |

#### 2.6 GertModelRefreshFeatureMap

- **Description**: Updates refreshable FeatureMap addresses in the host argument table according to a new FeatureMap base address. The table is copied to the device during a subsequent execution. Call after successful model loading; this interface does not refresh weight addresses.
- **Prototype**:

```c
int32_t GertModelRefreshFeatureMap(GertModelHandle model_handle, uintptr_t base_addr);
```

- **Parameters**:

| Parameter | Type | Input/Output | Description |
|------|------|----------|------|
| model_handle | GertModelHandle | Input | Valid handle returned by `GertModelLoad` |
| base_addr | uintptr_t | Input | New FeatureMap base address; must not be 0 |

- **Return value**: `int32_t`; `0` indicates success, and nonzero values are failure codes.

#### 2.7 GertModelGetStreamNum

- **Description**: Returns the number of streams required by the model. This count is fixed at compile time; the interface takes no model_handle and does not depend on model loading state. It returns the same result at any time after dlsym while the SO is alive. In external resource management scenarios, create streams based on this count and pass them to the model through `GertModelLoadConfig::external_streams`.
- **Prototype**:

```c
uint64_t GertModelGetStreamNum();
```

- **Parameters**: None.
- **Return value**: `uint64_t`; the number of streams required by the model.

#### 2.8 GertModelGetStreamDesc

- **Description**: Fills the output array with compile-time stream flags for stream creation. When `extended_attrs` is null, no model instance is required. When a `GertModelStreamDesc` is passed, it also returns internal streams of a loaded model, requiring a valid model instance handle.
- **Prototype**:

```c
int32_t GertModelGetStreamDesc(uint32_t *stream_flags, uint64_t stream_num, void *extended_attrs);
```

- **Parameters**:

| Parameter | Type | Input/Output | Description |
|------|------|----------|------|
| stream_flags | uint32_t * | Output | Must not be null; pbody fills in the flags for each stream |
| stream_num | uint64_t | Input | Array length; must match the value returned by `GertModelGetStreamNum`, otherwise an error is returned |
| extended_attrs | void * | Input/Output | May be `nullptr` or a `GertModelStreamDesc *`. Initialize a valid `model_handle` before calling to obtain the internal stream array and count |

- **Return value**: `int32_t`; `0` indicates success, and nonzero values are failure codes.

- **Parameter structure GertModelStreamDesc**: Passed through `extended_attrs` to query internal streams of a loaded model. The Executor currently uses this capability to set model stream priorities.

| Field | Type | Description |
|------|------|------|
| struct_size | uint64_t | Byte range of the structure provided for this call, usually the `sizeof` of the corresponding structure |
| model_handle | GertModelHandle | Valid handle returned by a successful `GertModelLoad`, before Unload |
| streams | aclrtStream * | Populated with a pointer to the model's internal stream array; read-only and valid after Load until Unload |
| stream_num | uint64_t | Populated with the actual stream count; older pbody versions do not populate it, leaving the pre-call value unchanged |

### 3. Executor Callback Interfaces (Implemented by the Executor, Called by pbody)

Callbacks are implemented by the Executor and injected into pbody through `GertModelLoadConfig::callbacks` (load time) and `GertModelRunConfig::run_callbacks` (execution time). All callbacks return `int32_t`; handling of return values is described for each callback. Except for the binary handle cache callbacks (3.3–3.6), the first argument is always `void *instance_handle`, whose value is passed back unchanged from `GertModelLoadConfig::instance_handle` so the Executor can identify its instance. Callbacks execute synchronously on the current calling thread; RunAsync makes device execution asynchronous, not callback execution on a background thread.

Nullability depends on usage: `GertModelLoadConfig::callbacks` itself must not be null. The lock/unlock/query/save/release callbacks used by the binary cache path must be supplied because current generated code calls them directly. `report_model_base_info` may be null, in which case reporting is skipped; `launch_func` may be null, in which case generated code launches tasks directly. `run_callbacks` and its pre/post-execution callbacks may be null, in which case they are skipped. Callback arguments are prepared by the model SO; fields to be populated by the Executor are identified in the descriptions.

#### 3.1 report_model_base_info (ReportModelBaseInfoFunc)

- **Description**: During `GertModelLoad`, pbody invokes this callback to report the `aclmdlRI` handle after initializing runtime resources and obtaining the handle. The Executor uses it to associate runtime information such as dump and profiling data.
- **Prototype**:

```c
int32_t (*ReportModelBaseInfoFunc)(void *instance_handle, const GertModelBaseInfo *info);
```

- **Parameters**:

| Parameter | Type | Input/Output | Description |
|------|------|----------|------|
| instance_handle | void * | Input | `GertModelLoadConfig::instance_handle` passed back unchanged |
| info | const GertModelBaseInfo * | Input | Model base information filled in by pbody; fields are listed below |

- **Parameter structure GertModelBaseInfo**:

| Field | Type | Description |
|------|------|------|
| struct_size | uint64_t | Byte range of the structure provided for this call; initialize to `sizeof(GertModelBaseInfo)` before calling |
| rt_model_handle | void * | `aclmdlRI *` created by codegen, available after pbody completes resource initialization (InitResources) |

- **Return value**: `0` indicates success; a nonzero value indicates reporting failure and causes pbody to abort loading.

#### 3.2 launch_func (GertModelLaunchFunc)

- **Description**: During model loading, pbody delegates generated tasks to the Executor through this callback while constructing/sinking tasks in `GertModelLoad`. This callback belongs to the Executor-side DFX callback set: when the DFX feature is enabled, the Executor assembles the callback and passes it to pbody via `GertModelLoadCallbacks::launch_func`; when the callback is null, generated code launches tasks directly through ACL/RT interfaces. The Executor selects a launch path according to `launch_info->launch_type` and may populate `launch_info->task_info->task_id` afterward for dump/profiling association. The callback executes on the loading thread; subsequent Run/RunAsync calls execute the constructed tasks through model execution interfaces.
- **Prototype**:

```c
int32_t (*GertModelLaunchFunc)(void *instance_handle, GertModelTaskLaunchInfo *launch_info);
```

- **Parameters**:

| Parameter | Type | Input/Output | Description |
|------|------|----------|------|
| instance_handle | void * | Input | `GertModelLoadConfig::instance_handle` passed back unchanged |
| launch_info | GertModelTaskLaunchInfo * | Input/Output | Task launch information filled in by pbody (task_id may be populated by the Executor); fields are listed below |

- **Parameter structure GertModelTaskLaunchInfo**:

| Field | Type | Description |
|------|------|------|
| struct_size | uint64_t | Byte range of the structure provided for this call; initialize to `sizeof(GertModelTaskLaunchInfo)` before calling |
| launch_type | GertModelTaskLaunchType | Launch type, determining the union member referenced by launch_params; values are listed below |
| task_info | GertModelTaskDesc * | Task DFX information; fields are listed below. task_id may be populated by the Executor after launch |
| launch_params | const GertModelTaskLaunchParams * | Parameters corresponding to the launch type (union); see below |

#### 3.3 lock_bin_handle_store / unlock_bin_handle_store (LockBinHandleStoreFunc / UnlockBinHandleStoreFunc)

- **Description**: Before accessing the Executor's cross-model binary handle cache, pbody enters the critical section through the lock callback and exits through unlock afterward. Loading follows this sequence: `lock → query → load binary on cache miss → save (record this reference) → obtain function handle → unlock`. A cache hit also requires save to increment the reference count; unloading calls release under the lock (see 3.6).
- **Prototype**:

```c
int32_t (*LockBinHandleStoreFunc)();
int32_t (*UnlockBinHandleStoreFunc)();
```

- **Parameters**: None.
- **Return value**: `0` indicates success, and nonzero values are failure codes.

#### 3.4 query_bin_handle_from_store (QueryBinHandleFromStoreFunc)

- **Description**: Queries the Executor's cache for a loaded binary handle by `bin_id`. A cache hit enables cross-model reuse and avoids repeated loading.
- **Prototype**:

```c
int32_t (*QueryBinHandleFromStoreFunc)(const char *bin_id, aclrtBinHandle *bin_handle);
```

- **Parameters**:

| Parameter | Type | Input/Output | Description |
|------|------|----------|------|
| bin_id | const char * | Input | Binary identifier string (UTF-8, `\0`-terminated), provided by pbody and valid for the duration of the call |
| bin_handle | aclrtBinHandle * | Output | Storage provided by pbody; the Executor writes the handle on a cache hit, or `nullptr` on a miss |

- **Return value**: `0` indicates a successful query, including a cache miss. A hit is determined by whether `*bin_handle` is non-null. A nonzero value indicates a query error and causes generated code to abort loading.

#### 3.5 save_bin_handle_to_store (SaveBinHandleToStoreFunc)

- **Description**: Records the model's reference to a binary handle. On first loading, saves the handle in the cache and sets the reference count to 1; on a cache hit, increments the reference count. This callback must be called whether the handle comes from the cache or from a new load.
- **Prototype**:

```c
int32_t (*SaveBinHandleToStoreFunc)(const char *bin_id, aclrtBinHandle bin_handle);
```

- **Parameters**:

| Parameter | Type | Input/Output | Description |
|------|------|----------|------|
| bin_id | const char * | Input | Binary identifier string (UTF-8, `\0`-terminated), provided by pbody and valid for the duration of the call |
| bin_handle | aclrtBinHandle | Input | Newly loaded or cached binary handle |

- **Return value**: `0` indicates success, and nonzero values are failure codes.

#### 3.6 release_bin_handle_from_store (ReleaseBinHandleFromStoreFunc)

- **Description**: Called by pbody when unloading a model or no longer using a binary. The Executor decrements the reference count and tells the caller whether the binary must actually be unloaded.
- **Prototype**:

```c
int32_t (*ReleaseBinHandleFromStoreFunc)(const char *bin_id, uint8_t *need_unload);
```

- **Parameters**:

| Parameter | Type | Input/Output | Description |
|------|------|----------|------|
| bin_id | const char * | Input | Binary identifier string (UTF-8, `\0`-terminated), provided by pbody and valid for the duration of the call |
| need_unload | uint8_t * | Output | Storage provided by pbody and populated by the Executor; `1` means the reference count has reached zero and pbody should unload the binary, while `0` means unloading is unnecessary |

- **Return value**: `0` indicates success, and nonzero values are failure codes.

#### 3.7 report_run_info_preprocess / report_run_info_postprocess (ReportModelRunFunc)

- **Description**: Provides execution-time DFX (profiling timing, dump dispatch, and so on). When callbacks are supplied and execution reaches their positions, preprocess fires before the argument table is copied and model execution is submitted; postprocess fires after the model execution interface returns successfully. Failure in an earlier step may skip the post callback. For RunAsync, the post callback indicates that execution submission has returned, not that device inference is complete.
- **Prototype**:

```c
int32_t (*ReportModelRunFunc)(void *instance_handle, const GertModelRunReportInfo *info);
```

- **Parameters**:

| Parameter | Type | Input/Output | Description |
|------|------|----------|------|
| instance_handle | void * | Input | `GertModelLoadConfig::instance_handle` passed back unchanged |
| info | const GertModelRunReportInfo * | Input | Execution report information filled in by pbody; fields are listed below |

- **Parameter structure GertModelRunReportInfo**:

| Field | Type | Description |
|------|------|------|
| struct_size | uint64_t | Byte range of the structure provided for this call; initialize to `sizeof(GertModelRunReportInfo)` before calling |
| model_id | uint64_t | Model ID |
| stream | aclrtStream | Execution stream; generated code fills this field with `nullptr` on synchronous Run and fills the execution stream only for asynchronous execution (RunAsync) |
| is_async | uint64_t | Whether execution is asynchronous; `0` means synchronous, nonzero means asynchronous |

- **Return value**: `0` indicates success; a nonzero value indicates callback failure. Current generated code ignores the return values of these two callbacks: it neither aborts execution nor logs an error at the call site based on them. If failure logging is needed, the callback implementation must handle it.

#### 3.8 hccl_load_task (HcclLoadTaskFunc)

- **Functionality**: Launch channel for HCCL communication tasks (HCOM/HVD/HVDWAIT) in static offline models. During model loading, while `GertModelLoad` sinks tasks, the model SO assembles the compile-time-fixed communication parameters into `HcclTaskParams` and passes them through this callback to the HCCL adaptation layer on the Executor side, which runs `PrepareTaskAsync` + `LoadTask` and registers the task handle. On model unload, the Executor uniformly unregisters the tasks (calling `UnloadTask` and releasing handles) before invoking `GertModelUnload`; this does not go through a model SO callback. For runtime launching, the function pointer is passed via `GertModelLaunchHcclParams::func_load_hccl`; see the union members in 3.2.
- **Version requirement**: A model containing HCCL communication operators requires `callbacks->struct_size` to cover the `hccl_load_task` field (that is, not less than `offsetof(GertModelLoadCallbacks, hccl_load_task) + sizeof(HcclLoadTaskFunc)`); otherwise `GertModelLoad` fails immediately with a prompt to upgrade the Executor. This callback is mandatory for models containing HCCL operators and fails when null.
- **Function prototype**:

- **Parameters**:

## Part II: OM2 Model Data

`gert_model_data.h` and `om2_package_contants.h` jointly define the data organization and directory structure of an OM2 package. The former describes the package manifest, models, and shared resources rooted at `GertModelData`; the latter defines their package paths, JSON keys, file categories, and compression rules. The serialization module follows these conventions to write model data into a ZIP archive.

To understand the package format, first map the members of `GertModelData` to directories and files, then examine the data structures referenced by those members. These structures describe the organization of serialized data; C++ object memory is not written directly to files. JSON fields and package file contents are covered in [Internal Structure of an OM2 Model Package](internal_structure_of_om2_model_for_dev.md).

### 1. gert_model_data.h

File location: `inc/framework/om2/model_data/gert_model_data.h`.

The following sections start with `GertModelData` and expand members depth-first in declaration order: the structures referenced by `manifest` and their children are covered first, then `models`, followed by `constants`, `kernels`, and `custom_ops`. Each data structure has its own three-column table (Field, Type, Description). Repeatedly referenced types are expanded only at their first occurrence; later references point to the corresponding subsection.

Smart pointers and containers are further expanded according to the custom types from this header that they reference or contain, until reaching primitive types, strings, or containers of primitive types. Sources of externally defined `ge::*` types are identified without repeating their definitions. `struct_size` defaults to the `sizeof` of the corresponding structure, and `reserved[4]` defaults to all zeros; neither is written to JSON. Tables use the complete C++ types from the header rather than abbreviations such as `String`, `Ptr<T>`, or `Array<T>`.

#### 1.1 GertModelData: Root Data Structure of an OM2 Package

`GertModelData` aggregates all data in an OM2 package and is the entry point for understanding the serialized format. Its members map to package files and directories as follows; paths are relative to the archive root prefix `<base_name>/`:

| Field | Type | Description |
|------|------|------|
| `struct_size` | `uint64_t` | Structure size in bytes, initialized to `sizeof(GertModelData)` by default; not written to the archive |
| `manifest` | `std::unique_ptr<GertModelDataManifest>` | Package manifest, corresponding to `manifest.json` |

| `custom_ops` | `std::unique_ptr<GertModelDataCustomOps>` | Custom operator artifact collection, corresponding to `data/custom_ops/binaries_npu_arch/` and `data/custom_ops/shared_libs/` |

#### 2.2 GertFileType and the Compression Whitelist

`GertFileType` defines package file categories; enum values increase from 0 in declaration order. `kGertCompressedFileWhitelist` is the whitelist of categories requiring compression. Packaging uses `IsGertFileCompressed(type)` to select DEFLATE for whitelisted categories and uncompressed Stored storage for others. The whitelist determines only the compression method, not whether a file is generated or allowed in the package.

| File Category | Numeric Value | Package Files | Compressed |
|----------|------|----------|----------|
| `kCsrc` | 0 | `data/model_%s/runtime/csrc/*` | Yes, whitelisted, DEFLATE |
| `kSo` | 1 | `data/model_%s/runtime/lib*.so` | Yes, whitelisted, DEFLATE |
| `kConstants` | 2 | `data/constants/constant_N` | No, Stored |
| `kConstantsConfig` | 3 | `data/model_%s/constants_config.json` | Yes, whitelisted, DEFLATE |
| `kVarWeight` | 4 | `data/variables/var_weight_data_N` | No, Stored |
| `kVariablesConfig` | 5 | `data/model_%s/variables_config.json` | No, Stored |
| `kKernels` | 6 | `data/kernels/*` | No, Stored |
| `kCustomKernels` | 7 | `data/custom_ops/*` | No, Stored |
| `kModelMeta` | 8 | `data/model_%s/model_meta.json` | No, Stored |
| `kOpAttr` | 9 | `data/model_%s/op_attr.json` | Yes, whitelisted, DEFLATE |
| `kVisualJson` | 10 | `data/model_%s/debug/ge_visual_*.json` | Yes, whitelisted, DEFLATE |
